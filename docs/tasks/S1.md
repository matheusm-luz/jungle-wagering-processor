# S1 — Domain core

**Goal:** the pure domain model — `Money`, `WalletLedgerEntry`, `Wallet`, `WagerTransaction` with its state machine, failure codes and domain errors — with every invariant enforced inside the classes and proven by unit tests with no I/O.

Requirements: R-15 to R-19, R-21 to R-28 (domain side only; R-20 is purely a schema guarantee and belongs to S2). Decisions: ADR-02, ADR-03 (the transaction carries the observed balance), ADR-06 (failure codes), ADR-10, ARCHITECTURE §2 step 9 and §5. Interpretations: L-02, L-03, L-16, and L-17 and L-18, which this slice raised.

## Subtle points

- **Transaction boundary, lock, ack, outbox:** not touched. This slice has no I/O; ids and time are passed in by the caller, so the domain needs no port.
- **Idempotency:** only the domain hook, `matchesPayload(payloadHash)`. The canonical hash itself is S4.
- **Balance and ledger cannot diverge inside the aggregate.** `Wallet.debit` and `Wallet.credit` are the only ways to change the balance, and each one returns the `WalletLedgerEntry` it produced. The entry's `sequence` is the wallet version it produced, which is what `UNIQUE (wallet_id, sequence)` will check in S2.
- **Opening.** A wallet is at version 1 after creation whether or not it has an opening balance (statement §6.2 and the `POST /wallets` example). A positive opening balance returns the `CREDIT` entry with `sequence` 1; a zero one returns none.
- **Negative money exists only as a computed value.** `Money.from` is the input contract and refuses a negative amount; `subtract` and `negate` may produce one (reconciliation difference). `Wallet` and `WalletLedgerEntry` refuse it.
- **A failed operation leaves the aggregate unchanged.** Every guard runs before the first assignment.
- **A credit can overflow.** A balance beyond `NUMERIC(19,2)` throws `MoneyOutOfRangeError`, not `InvalidMoneyError`: the request was valid, so the outcome depends on state and must not be answered as a malformed payload. S4 decides the outcome.
- **Immutability does not stop at `Object.freeze`.** A frozen object still hands out a mutable `Date`, so every class keeps its instants as epoch milliseconds and returns a fresh `Date` on each read.
- **A status and its failure code are paired in the domain.** `reject` refuses `PROCESSING_FAILED` and `fail` accepts nothing else, as in the table of ARCHITECTURE §6.
- **`ledgerDirectionFor` checks the reference it is given** against the declared provider and external id. For a `ROLLBACK` the wrong transaction would invert the direction of the money.
- **`rehydrate` never validates**, on every class: it rebuilds state the database already accepted.
- **Insufficient balance is one domain error, two failure codes.** `Wallet.debit` throws `InsufficientFundsError`; the use case decides between `INSUFFICIENT_FUNDS` (S4) and `REVERSAL_WOULD_OVERDRAW` (S6).
- **Out of this slice on purpose:** the reference rules of statement §7.2–7.5 (S6), the canonical hash (S4), integration events (S4), the counterparty account of ADR-12 (S2 and S3), retry bookkeeping of pending references (S7).
