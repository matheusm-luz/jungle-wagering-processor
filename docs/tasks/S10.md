# S10 — Outbox publisher

**Goal:** every instance publishes the committed outbox rows to the SNS FIFO topic in batches locked with `FOR UPDATE SKIP LOCKED`, marks them published in the same transaction, retries failures with backoff without ever dropping an event, and a crash before or after the publish ends with every event delivered under its own `eventId`.

Requirements: R-08, R-57, R-69, R-71; R-63 (concurrent publishers, restart recovery); L-14.

## Subtle points

- **Transaction boundary.** The business transaction only inserts outbox rows; nothing is published before its commit, because the publisher only sees committed rows (`READ COMMITTED`). The publisher's own transaction is select-lock → publish → mark → commit; it holds a pool connection during one bounded network call (ADR-04).
- **Lock.** Row locks on outbox rows only, with `SKIP LOCKED`: publishers never wait for each other and never touch a wallet row. A dead publisher's locks go with its connection.
- **Idempotency.** At-least-once: a crash after the publish and before the commit republishes the same rows. `MessageDeduplicationId` = event id makes the broker drop the copy within five minutes; past that, consumers deduplicate by `eventId` (ADR-11, L-14).
- **Ack.** Not touched: SQS acks stay after the business commit (S9).
- **Outbox.** This is the slice. Ordering: within one batch, rows go in `next_attempt_at` order and FIFO keeps the order per group; two publishers can invert two batches of one wallet, and a retried row is published after later ones (L-14: consumers order by `walletVersion`).

## Decisions (Matheus, 13 Nov)

- **Q1 — `OutboxMessage` in the domain: (a).** `src/domain/outbox-message.ts` follows statement §6.5 (`enqueue`, `rehydrate`, `isPending`, `isDue`, `markPublished`, `scheduleRetry(now, policy)`); the unit of work enqueues through it and the publisher rehydrates the locked rows. `InboxMessage` stays SQL, as S9 left it.
- **Q2 — L-14 accepted as written.** Per-wallet order is best-effort across batches; consumers order by `walletVersion` and deduplicate by `eventId`.

## Notes from implementation

- **Test order.** T1 and T3 were test-first and seen failing (missing module; missing defaults). T4 was seen failing on the missing publisher module, then passed. The publisher was written whole in T4, so the cases of T5 to T8 and T9 to T11 passed on their first run; mutation runs show which are not vacuous (next note).
- **Mutation runs.** (M1) the `SKIP LOCKED` lock mode removed: the in-process skip-locked case fails; the cross-process cases still pass, because the broker deduplicates a double publication by event id, so R-69 across processes proves no loss and no duplicate delivery, and the lock itself is proven in process. (M2) the shutdown not awaiting the batch: the shutdown case first passed anyway, because the SQS consumer's own shutdown (its open long poll) ran before the publisher's hook and delayed it; the case now holds the lock for 2 s after `close()`, and then fails under M2. (M3) a random deduplication id: the in-process first-publication and duplicate cases fail, and across processes the crash-after-publish and restart cases fail. Each mutation was reverted.
- **A partial `PublishBatch` failure** was first left untested; see the PR review below.
- **Test isolation.** Both outbox files mark every unpublished row of the shared suite database as published in `beforeAll`: those rows belong to other suites, and a publisher would otherwise spend the file draining them. The `test` service idles the publisher (`OUTBOX_POLL_INTERVAL_MS=1000000000`); the S10 tests turn it on per instance.
- **Docker Desktop stopped once during the run** (13 Nov); it was restarted and the suites were rerun from scratch.

## Independent review (13 Nov)

The `invariant-reviewer` found no blocker and no major; six minors. Fixed in a second commit at Matheus's request (m1, m2, m5, m6 in code; m3, m4 in the documents).

- **m1 fixed.** A host that vanishes without closing its socket held its outbox (or wallet) locks until the TCP keepalive, hours. `DATABASE_IDLE_IN_TRANSACTION_TIMEOUT_MS` (15 s, above the publish timeout, enforced by `loadEnv`) goes in the startup packet of every application connection, as `lock_timeout` does. Test: `test/integration/unit-of-work.test.ts` "a session idle inside its transaction past the timeout is ended by the server, and its wallet lock released", seen failing before the setting (the waiter timed out after 2 s).
- **m2 fixed.** The publish timeout had no test. New case "a broker that accepts the connection and never answers is abandoned after the publish timeout: the rows are rescheduled, not held" (a local socket that never answers; the broker is not replaced). Mutation: the `abortSignal` removed → it fails. This also confirms that the SDK honours `abortSignal` under Bun.
- **m3 recorded.** A broker that accepts and always answers late duplicates past the deduplication window on every retry; ADR-04 states it, S11's metrics should show `attempts > 1`.
- **m4 recorded.** Order within a batch depends on the clocks of the instances; ADR-04 and L-14 state it.
- **m5 fixed.** Poll intervals above 2³¹−1 ms (where `setTimeout` fires at once) are refused, for the outbox and the pending-reference worker; a retry cap below its base is refused for both. Test: `test/unit/config/env.test.ts` "refuses a poll interval setTimeout cannot hold, …", seen failing first.
- **m6 fixed.** The crash tests raced the failpoint against the harness's readiness check. The failpoint process now starts while nothing is pending and a second process commits the events, so it cannot die before it is ready. The crash-after-publish case now accepts that the dead process may have published only the opening's batch, and asserts that the survivor delivers exactly the rest. Mutation M3 (random deduplication id) still fails it.
- **Found while fixing.** The LocalStack healthcheck counted every SNS subscription, so a test topic left by a suite that failed before its `afterAll` (one did, in the m2 mutation run) made LocalStack unhealthy and stopped every later run. It now counts only the subscriptions of `wager-events.fifo`; checked by creating a stray subscription and running the healthcheck.

## PR review (13 Nov)

One should-fix: no test went through a batch the broker accepts in part, so treating every id of the batch as accepted (events marked published that never left) broke nothing, and T6 claimed the case. LocalStack 4.12 cannot produce a partial answer: an empty attribute and an oversized entry each fail the whole call, an empty body is accepted (probed by hand). At Matheus's choice the case is tested with the real database and SDK and a forged HTTP answer in the documented `PublishBatch` shape, the one exception to invariant 8, recorded in `CLAUDE.md`. Test: "a batch the broker accepts in part: …" — two entries accepted and marked, two refused, logged and rescheduled with `attempts = 1`, then published to the real topic. Mutation: every batch id treated as accepted → it fails. Restored.
