# S12 — Failure modes

**Goal:** a transient infrastructure failure never loses or duplicates money and never leaks detail: over HTTP it is a 503 with `Retry-After` and the instance reports not ready; the SQS consumer and the outbox publisher back off while SQS or PostgreSQL is unreachable and recover on their own once it returns; a pending reference whose retry keeps failing for a non-transient reason ends `FAILED` with `PROCESSING_FAILED`.

Requirements: R-14 (no duplicated credit or debit, no lost confirmed event, no negative balance), R-63 (failure recovery on real containers). Decisions: ADR-01, ADR-04, ADR-05, ADR-06; findings left for S12 in `docs/PROGRESS.md` (S4 m4, S6 m2, S9 Q2 and m9, S10, S11 m1).

## Subtle points

- **Transaction boundary.** A transient error rolls the whole unit of work back before the 503 is written, so a resend with the same key starts from nothing. Marking a row `FAILED` happens in a new transaction after the failed one rolled back, under the wallet lock, re-checking the row is still waiting (like `postpone`).
- **Lock.** 55P03 is transient everywhere: 503 over HTTP, retry on SQS, postpone in the worker. It must never count towards `FAILED`.
- **Idempotency.** 503 is safe to resend with the same key: usually nothing was committed, and if the connection dropped during `COMMIT` after the server committed, the resend replays the original result (S12 review). The tests prove the resend processes once.
- **Ack.** With PostgreSQL down the consumer must not ack: the message returns after its visibility backoff.
- **Outbox.** No event is lost while SNS is down: the rows stay, `attempts` grow, and each is published once after recovery.

## Decisions (Matheus, 14 Nov)

All three proposals accepted: Q1 (a) TCP proxy, Q2 (a) non-transient errors count attempts, Q3 (a) 422.


- **Q1 — How "down" is simulated.** PLAN says "stop and start each container". (a) A TCP proxy in the test process, between the app and the real container, that the test cuts and restores: real PostgreSQL, real LocalStack, real driver and SDK; deterministic and fast; no Docker socket in the test container. It does not reproduce a server restart (lost sessions are reproduced by dropping the proxied sockets). (b) Mount the Docker socket in the `test` service and `docker stop`/`start` the containers: literal, but LocalStack loses its queues on restart (re-created by its init script, test queues are not), restarts take ~10 s each, every other suite sharing the containers is affected, and the test container gets control of the host's Docker. (c) `docker pause`/`unpause`: same socket cost, models a hung server, not a dead one. Proposal: (a), and the PLAN row is updated.
- **Q2 — When a pending reference becomes `FAILED`.** (a) A retry that throws a non-transient error (T1) counts an attempt; at the 10th (the same `PENDING_REFERENCE_MAX_ATTEMPTS`) it becomes `FAILED` with `PROCESSING_FAILED`, in its own transaction, with a `WagerTransactionRejected`-shaped event carrying status `FAILED`; a transient error is still postponed without counting. (b) `FAILED` at the first non-transient error. (c) No automatic `FAILED`: document it as reserved and keep the postpone. Proposal: (a); a bug that fails once does not burn the transaction, and an outage never fails one.
- **Q3 — HTTP status of a `FAILED` transaction (replay or query).** (a) 422 with `status: FAILED` and `failureCode: PROCESSING_FAILED`: terminal, resending replays it, like a rejection. (b) 500 with the same body: says "our fault", but many clients retry 5xx forever and get the same answer. Proposal: (a).

## Notes from implementation

- **Test order.** T1 failed on the missing module, T2 on `pg_sleep` finishing (no timeout), T3 on 500 instead of 503 (three cases), the worker cases of T7 on `postpone` never counting; each passed after its code. The resolver cases of T7 were run against the previous resolver after the fact (mutation): all three fail. T5 and T6 passed on their first run: the consumer, the publisher and the readiness probe already backed off and recovered; each test asserts the failure logs (or `attempts >= 2`) before restoring, so a proxy that cut nothing would fail it.
- **Behaviour changed in older tests.** `log-audit` and `metrics` drove a 55P03 over HTTP and expected the 500 that ADR-01 said S12 would replace; they now expect 503, and the audit checks that the 503 line carries `correlationId` and `errorCode` instead of looking for an `error` line. `test/concurrency/sqs-consumer.test.ts` holds a wallet for 20 s on purpose and now raises `DATABASE_STATEMENT_TIMEOUT_MS` too, because the statement timeout also bounds a lock wait (the env refuses a statement timeout not above the lock timeout).
- **500 bodies.** A non-transient `DriverException` is now answered by the filter itself, `{ statusCode: 500, message: 'Internal server error' }` as Nest did, and logged as `request failed` with `errorName`, `errorCode` and `constraint` only (S6 m2).
- **Not done.** The SQS read of the scrape-time DLQ gauge still has no timeout (S11 m1): the database read is now bounded by the statement timeout.
- **Review (14 Nov, PR #12).** Must fix: two workers whose retries failed on the same due row both postponed it and counted two attempts for one round, so a row could reach `FAILED` before 10 rounds. `postpone` now re-checks under the wallet lock that the row is still due, as `retry` does. Test: "two workers postponing the same failed round count one attempt: …", seen failing first (`postponed` instead of `skipped`). Nice to have: the reason a 503 is safe to resend now covers a connection lost during `COMMIT` (filter, ADR-05, this file).
- **Independent review (14 Nov).** No blocker. Fixed in a third commit at Matheus's request: M1 (`ENOTFOUND`, `EAI_AGAIN`, `EHOSTUNREACH` and `ENETUNREACH` are transient: a stopped Compose service leaves the network, and a request answered 500; test "a request is 503 and the instance is not ready, as when a stopped Compose service leaves the network", seen failing with 500), M2 (the 500 branch for a non-transient driver error had lost its only test when the log audit's 55P03 became a 503; `test/unit/infrastructure/error-filter.test.ts` passed on its first run and fails with the branch removed), m5 (the two postpones now race through `Promise.all`), m6 (`POST /wallets` has no key: a resend after a committed opening is 409, documented in ADR-05 and §6), m7 (the shared `reference_attempts` written in L-07). M3 (a PostgreSQL outage longer than about 75 s dead-letters SQS messages) stays documented, for the S13 README. m4 (no end-to-end test of a real non-transient error through the worker to `FAILED`; each half is tested) is not done.
- **Found: a long PostgreSQL outage dead-letters SQS messages.** Each failed receive counts towards the redrive policy, so with the ADR-05 backoff (5, 10, 20, 40 s) a message received during an outage longer than about 75 s reaches the DLQ instead of waiting. Nothing is lost (the DLQ keeps it and a redrive replays it idempotently), but it needs an operator. Recorded in ARCHITECTURE §9; the fix (stop receiving while the database is unreachable) is offered to Matheus, not built.
