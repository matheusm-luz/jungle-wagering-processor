# S2 — Schema and migrations

**Goal:** one hand-written, reversible SQL migration that creates every table, constraint, index and trigger of ARCHITECTURE §3, each guarantee proven by an integration test against the real PostgreSQL container.

Requirements: R-03, R-09, R-13, R-20, R-21 (schema side). Decisions: ADR-01 (defence in depth), ADR-02 (`NUMERIC(19,2)` + `CHAR(3)`), ADR-03 (the transaction row is the idempotency record, with the observed balance), ADR-05 (pending-reference bookkeeping), ADR-12 (`ledger_accounts` and the counterparty column), ADR-13 (hand-written SQL, static list). Interpretations: L-01, L-03, L-08, L-16, L-18. Findings from S1: `sequence` and `version` are `INTEGER`; the observed balance has its own currency.

## Subtle points

- **Transaction boundary:** the migration runs in one SQL transaction (`transactional`, `allOrNothing`, proven in S0), so a failed `up` leaves no half schema. Runtime transactions are not touched yet.
- **Lock:** none is taken here. `UNIQUE (wallet_id, sequence)` and `CHECK (balance >= 0)` are the backstop of ADR-01: they make a lost update or an overdraft fail at commit even if the lock were missing.
- **Idempotency:** `UNIQUE (idempotency_key)` and `UNIQUE (provider_id, external_transaction_id)` are what turn a race that escapes the wallet lock (same key, another wallet) into a rollback and a 409 (ARCHITECTURE §2). The single-reversal partial index only counts `PROCESSED` rows, so a rejected reversal can coexist with the applied one.
- **Inbox:** primary key `(consumer_name, message_id)`; inserting it first inside the transaction is S9.
- **Outbox:** pending scan is a partial index on `next_attempt_at` where `published_at is null`. `next_attempt_at` is `NOT NULL` and starts at `occurred_at`, so the publisher query of S10 needs no `OR … IS NULL`.
- **Defence beyond ARCHITECTURE §3, at one line each:** composite foreign keys make an entry's currency equal to its wallet's and its account's, and its wallet equal to its transaction's wallet; the update trigger on `wager_transactions` also freezes the identity columns of a non-terminal row. They protect the ledger invariant without changing any decision.
- **Tests cannot clean the ledger** (that is the point of the triggers), so every test uses fresh ids and the ledger invariant is checked over the whole database.
- **Out of this slice:** MikroORM records and mappers (S3, with their first use), `correlation_id` on the transaction (L-15 is still proposed; S4 adds it with a migration of its own if accepted), statement and lock timeouts (S4 and S12).
