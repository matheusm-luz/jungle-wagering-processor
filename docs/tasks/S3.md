# S3 — Open and read a wallet

**Goal:** `POST /wallets` commits the wallet, its internal `OPENING` transaction, the `CREDIT` entry against the `FUNDING` account and the outbox events in one SQL transaction, a duplicate is a 409, and `GET /wallets/:walletId` returns the persisted wallet.

Requirements: R-22 and R-24 (persistence side), R-43, R-44 (wallet query only; the transaction queries are S8). Decisions: ADR-02, ADR-03 (the transaction row and its hash), ADR-06 (status), ADR-10 (records and mappers), ADR-12 (counterparty rule in the domain, `FUNDING` created on first use), ADR-13 (forked `EntityManager`, `em.transactional()`). Findings from S1 and S2: ids and time are application ports; mappers turn `NULL` into `undefined`; constraint names drive the error mapping.

## Subtle points

- **Transaction boundary:** one `em.transactional()` on a forked `EntityManager` per request (ADR-13). Each write is a native `INSERT` sent at once, in foreign-key order (wallet, `OPENING` row, entry, outbox rows), so a unique violation surfaces at the write that caused it; the rollback of `em.transactional()` undoes all four. T5 proves the rollback with a failure after every write, not only with the duplicate.
- **Lock:** none on the wallet: it does not exist yet. `UNIQUE (player_id, currency)` is the only serialisation between two concurrent openings, and the loser maps to 409 by constraint name (`error.constraint`, copied from the `pg` error by MikroORM's `DriverException`). The first use of a `FUNDING` account makes a concurrent opening in the same currency wait on the unique index until the first commits; afterwards `DO NOTHING` and a new statement see the committed row.
- **Idempotency:** `POST /wallets` has no `Idempotency-Key` (statement §9): a repeat is a 409, not a replay. The `OPENING` row still has to satisfy the idempotency constraints of every transaction (see Q2).
- **Ack:** not touched.
- **Outbox:** rows written in the same transaction, `next_attempt_at = occurred_at`, `aggregate_id = walletId` (the future `MessageGroupId`, ADR-11). Nothing publishes them until S10.

## Decisions taken by Matheus (13 Nov)

- **Q1 Outbox in S3.** `PLAN.md` puts the outbox in S3, while the S1 findings said the integration events would arrive with S4. Decided: the event classes are built now; a positive opening emits `WagerTransactionProcessed` and `WalletBalanceChanged`; a zero opening emits nothing (no transaction, no balance change). Rejected: deferring the outbox to S4; an extra `WalletOpened` event.
- **Q2 Identity of the `OPENING` row.** Decided: `providerId = 'SYSTEM'`, `externalTransactionId = idempotencyKey = 'opening:<walletId>'`, `roundId = gameId = 'OPENING'`, `payloadHash` from the same canonical hash as every other transaction (T3). `SYSTEM` is reserved to `OPENING` by the schema (`wager_transactions_system_provider_only_for_opening`, added after the review): without it a caller could claim `providerId: "SYSTEM"` and name a predictable `opening:<walletId>` as a reference. Rejected: the transaction's own UUID as external id; an ad hoc hash.
- **Q3 Data of `WagerTransactionProcessed`.** The statement defines only `WalletBalanceChanged`. Decided: `transactionId`, `providerId`, `externalTransactionId`, `walletId`, `playerId`, `kind`, `money`, `referenceExternalTransactionId` when present, `balance` (the observed balance) and `walletVersion`. Rejected: a minimal payload without balance and version.
