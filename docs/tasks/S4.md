# S4 — Process `BET`, `WIN`, `LOSS` over HTTP

**Goal:** `POST /wagering/transactions` runs the critical section of ARCHITECTURE §2 for `BET`, `WIN` and `LOSS` — wallet lock, idempotency lookup, movement, transaction, entry against the provider's settlement account, wallet update and outbox events in one SQL transaction — and answers replay, conflict, rejection and invalid input with the statuses of ARCHITECTURE §6.

Requirements: R-29 (gameplay part), R-30, R-31 (without reference), R-32, R-39, R-46, R-47, R-48 (200, 400, 404, 409, 422; 202 is S7, 503 is S12), R-58 (three of the four events; `WagerTransactionPendingReference` is S7), R-59. Decisions: ADR-01 (lock), ADR-03 (transaction row as idempotency record, canonical hash), ADR-06 (status from the persisted state), ADR-12 (posting against `PROVIDER_SETTLEMENT`), ADR-13 (forked `EntityManager`). Findings from S1–S3: `MoneyOutOfRangeError` needs an outcome; `walletId` must be a UUID before any query; `SYSTEM` is refused with 400; provider identifiers follow the `playerId` rules (1 to 128 characters, no U+0000).

## Subtle points

- **Transaction boundary:** one `UnitOfWork.run` per request. Validation, the hash and the ids happen before it opens; the time of the movement is read after the lock. Inside: lock, lookup, rule checks, then the writes in foreign-key order (transaction, entry, wallet update, outbox). The response is built only after `run` returns, that is after `COMMIT`.
- **Lock:** `SELECT … FOR UPDATE` on the wallet row is the first statement (ADR-01). At `READ COMMITTED` the lookup that follows sees whatever the previous holder committed, so a replay of the same request on the same wallet always finds the first row. The wallet update also carries `version = <locked version>`: under the lock it always matches, and if it ever did not, the write fails instead of losing an update (defence in depth with `UNIQUE (wallet_id, sequence)`).
- **Idempotency:** the transaction row is the record (ADR-03). Lookup by key or by provider + external id under the lock. Two rows of different wallets are not serialised by the lock; the unique index refuses the second insert and the error is mapped to 409 directly. That is always right: a violation of `idempotency_key` with the same hash is impossible, since the same hash means the same `walletId` and therefore the same lock.
- **Ack:** not touched (S9).
- **Outbox:** `WagerTransactionProcessed` + `WalletBalanceChanged` for `BET` and `WIN`; `WagerTransactionProcessed` only for `LOSS`; `WagerTransactionRejected` for a rejection. Written in the same transaction; a replay writes nothing.

## Choices made without a question (Matheus may overrule)

- **Body of a 422.** The same body as a 200, plus `failureCode`: `{ transactionId, status, failureCode, balance, idempotentReplay }`. ARCHITECTURE §6 says the provider reads `failureCode`, and a replay answers it identically. Since the review, `WALLET_PLAYER_MISMATCH` has no `balance` (L-20).
- **References wait for S6.** In S4 the request schema accepts only `BET`, `WIN` and `LOSS` and has no `referenceExternalTransactionId`; S6 opens both. Until then a `REFUND` is a 400.
- **Identifier limits.** `providerId`, `externalTransactionId`, `playerId`, `roundId` and `gameId`: 1 to 128 characters, no U+0000. `Idempotency-Key`: 1 to 256 visible ASCII characters (the recommended `{providerId}:{externalTransactionId}` reaches 257 only at both maximums; 256 is enough for any realistic id).
- **Unknown wallet before the idempotency lookup.** A key already used, resent with an unknown `walletId`, is 404, not 409: the lock comes first (ARCHITECTURE §2, step 5).

## Decisions taken by Matheus (13 Nov)

- **Q1 Credit beyond the storable range.** `Wallet.credit` throws `MoneyOutOfRangeError` when the new balance exceeds `NUMERIC(19,2)` (S1 finding). Decided: persisted `REJECTED` with a new code `BALANCE_LIMIT_EXCEEDED`, 422, `WagerTransactionRejected`; a migration extends `wager_transactions_failure_code_valid`. Rejected: `FAILED` with `PROCESSING_FAILED` (a predictable state limit, not an infrastructure error); a 422 that is not persisted (non-deterministic replay).
- **Q2 Data of `WagerTransactionRejected`.** Decided: the data of `WagerTransactionProcessed` plus `failureCode`: `transactionId`, `providerId`, `externalTransactionId`, `walletId`, `playerId`, `kind`, `money`, reference when present, `failureCode`, the observed `balance`, `walletVersion`. Rejected: a minimal payload without balance and version.
- **Q3 L-15, storing `correlationId`.** Decided: deferred to S7, where the worker emits events long after the request. In S4 every event is built inside the request, with the correlation id of its log context. Rejected: adding the column now, unused until S7.
