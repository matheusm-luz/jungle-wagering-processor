# S5 — Multi-process harness and first concurrency tests

**Goal:** a test helper spawns three real application processes (`bun src/main.ts`) against the suite's PostgreSQL and LocalStack, and the first concurrency suite proves, across those three processes, that a wallet is never debited twice, never goes negative and never blocks another wallet, ending every test with the ledger invariant.

Requirements: R-64, R-65, R-66, R-67, R-72 (for this suite; every earlier integration file already ends with it). Decisions: ADR-01 (per-wallet `SELECT … FOR UPDATE`), ADR-03 (transaction row as idempotency record), ADR-09 (three real processes spawned by the runner, inside the Linux test container). Caveat carried from S4: R-39 and R-47 were proven in one process; this suite proves them across three (R-47 since the review, m3).

## Tasks

- [x] **T1 `test:concurrency` script.** `package.json`: `docker compose --profile test run --rm --build test bun test ./test/concurrency`, the same image and container as the integration suite. Proven by T3 running through it.
- [x] **T2 Process harness.** `test/support/processes.ts` — `startProcesses(count)`: picks a free port per process, spawns `bun src/main.ts` with the suite environment and that `PORT`, waits for `/health/ready` to answer 200, and returns `{ urls, pids, stop() }`; `stop()` sends `SIGTERM` and awaits every exit. A process that exits before it is ready fails the setup with its exit code and stderr.
- [x] **T3 Three processes (R-67).** Test first, `test/concurrency/wallet-races.test.ts` — "three separate application processes are ready and each one serves requests": three distinct pids other than the runner's, and a wallet opened through each URL is read back through the other two.
- [x] **T4 Same bet 50 times (R-64, R-39).** Same file — "the same bet sent 50 times in parallel across three processes debits once": all 50 answers 200 with the same `transactionId` and balance, exactly one with `idempotentReplay: false`; one transaction row, one entry, two outbox rows; balance `75.00`, version 2.
- [x] **T5 Competing bets (R-65).** Same file — "balance 100 and two bets of 80 on different processes: one PROCESSED, one REJECTED, balance 20, one debit", run on 20 wallets at once so the requests really overlap; and "60 bets of 5.00 on a wallet of 100: exactly 20 applied, 40 INSUFFICIENT_FUNDS, balance 0.00, never negative".
- [x] **T6 Distinct wallets in parallel (R-66).** Same file — "a wallet held locked does not delay a bet on another wallet": the runner holds `SELECT … FOR UPDATE` on wallet A, a bet on A is seen waiting in `pg_stat_activity`, a bet on B through another process answers 200 meanwhile, and A's bet completes after the release; and "30 wallets with 10 bets each, all in parallel across three processes, all end at 90.00 and version 11".
- [x] **T7 Ledger invariant (R-72).** `afterAll` of the suite runs `expectLedgerInvariant` before the processes stop, as every integration file does.
- [x] **T7b Review fixes.** After the `invariant-reviewer` (13 Nov), at Matheus's request: m1, the observed balances of the 60-bet test are compared as strings, never as `number`; m2, the harness refuses duplicate probe ports before spawning; m3, R-47 across processes, "one key with two payloads sent in parallel to different processes: one 200, one 409 IDEMPOTENCY_KEY_CONFLICT, one debit"; m5, the R-66 test waits for a session that `pg_blocking_pids` says is blocked by the runner's own backend, not for any session waiting on a lock; m4 and m6 recorded in `docs/PROGRESS.md` for S12 and S9.
- [x] **T8 Definition of done.** `/verify` with real output (adds `test:concurrency`); matrix rows R-64 to R-67 and R-72; `CLAUDE.md` Commands (`test:concurrency` exists); `docs/PROGRESS.md`; one commit.

## Subtle points

- **Transaction boundary:** unchanged from S4. The suite only observes it from outside: every answer is read after the process committed, so the rows asserted after `Promise.all` are final.
- **Lock:** the subject of the slice. R-65 depends on the second debit reading the balance committed by the first, which `FOR UPDATE` at `READ COMMITTED` guarantees; R-66 shows the lock is per wallet row, not global, by holding one row from the runner and watching another wallet progress.
- **Idempotency:** R-64 sends one key 50 times. All requests carry the same `walletId`, so they serialise on the wallet lock and every one after the first finds the row by key; the unique index is not needed here (it is the backstop for the cross-wallet case of S4).
- **Ack and outbox:** not touched. The outbox rows are counted to show a replay writes no event.

## Choices made without a question (Matheus may overrule)

- **Free port by probe.** The harness binds port 0, reads the port and releases it before spawning. A released probe port can be handed out again, so the harness refuses duplicate ports before spawning (review m2); whether a second listener on a taken port would fail was not checked, and the refusal makes it irrelevant. The test container runs nothing else.
- **Process logs off.** The processes run with `LOG_LEVEL=silent` from the test container; stderr is kept only to explain a failed boot. S9 and S11 can turn logs on when a test needs to read them.
- **Separate folder and script.** `test/concurrency/` runs only through `test:concurrency`, so `test:integration` keeps its time and the plan's command table stays true.

## Test order

T3 was test-first and failed for the expected reason (`Cannot find module '../support/processes'`). T4 to T6 test code that already existed since S4, so they passed on their first run. A mutation run without `LockMode.PESSIMISTIC_WRITE` in `mikro-orm-unit-of-work.ts` made all five of them fail ("the bet on the locked wallet never waited" for the lock test, wrong counts for the others), so none is vacuous. In that run the ledger invariant still held: the version guard of `wallets.update` and `UNIQUE (wallet_id, sequence)` refused the lost updates, which is the defence in depth ADR-01 describes.

Mutation runs after the review fixes (13 Nov):

- **Without `PESSIMISTIC_WRITE`:** the four race tests fail; the R-66 test now passes, correctly. Without the application's lock the bet on the held wallet still blocks, later, on its `UPDATE wallets`, and `pg_blocking_pids` sees that. The old wait matched `for update` in the query text, which is why it failed before. R-66 is about the absence of a global lock, not about the application taking the row lock (the race tests and the S4 lock test prove that).
- **With a global lock** (`pg_advisory_xact_lock(42)` before the wallet lock): the R-66 test fails (timeout: the bet on the free wallet waits behind the held one).
- **With the hash comparison disabled** in `ProcessWagerTransaction`: only the new m3 test fails.
- **With a failing `expect` in `afterAll`:** `bun test` exits 1 and reports it, so a broken ledger invariant fails the suite (R-72).
