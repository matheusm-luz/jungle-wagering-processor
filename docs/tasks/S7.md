# S7 — Pending references

**Goal:** a transaction waiting for its reference emits `WagerTransactionPendingReference`, and a worker in every instance retries it under the wallet lock with exponential backoff until the reference is applied, rejected by a reference rule, or the attempts run out (`REJECTED` with `REFERENCE_NOT_FOUND` and an event).

Requirements: R-40, R-70, and the pending parts of R-42 (`REFERENCE_NOT_FOUND`), R-48 (202) and R-58 (`WagerTransactionPendingReference`). Decisions: ADR-01 (wallet lock first), ADR-05 (backoff `min(60s, 1s × 2ⁿ)`, 10 attempts, re-check under the lock), ADR-06, L-05, L-10, L-15.

## Subtle points

- **Lock.** The scan is a plain read with no lock. Each row is then retried in its own transaction that locks the wallet first and re-reads the row under the lock: if it is no longer `PENDING_REFERENCE` or no longer due, another worker got there first and the row is skipped. That re-check is what makes two workers safe; `SKIP LOCKED` is not needed because the lock order (wallet, then rows of that wallet) is the same as on the request path, so no deadlock.
- **Transaction boundary.** One retry = one `UnitOfWork.run`: the row's new state, the entry, the wallet update and the events commit together. The terminal update is `WHERE status = 'PENDING_REFERENCE'`, so a miss is a bug, never a silent second application.
- **Idempotency.** A replay of the original key after the worker resolved it answers from the row: 200 `PROCESSED` (or 422), not 202 (L-05). The key's hash is unchanged; the trigger forbids changing identity columns.
- **Outbox.** `WagerTransactionPendingReference` once, when the row starts to wait; nothing on a failed retry; `WagerTransactionProcessed` + `WalletBalanceChanged`, or `WagerTransactionRejected`, when it leaves.
- **Ack.** None here: SQS is S9.
- **Unexpected error on one row** (shortcut): logged, the row stays due and is retried at the next poll. Turning it into `FAILED` is S12.

## Decisions (Matheus, 13 Nov)

- **Q1 Correlation id of worker events (L-15).** (a): `correlation_id` is stored on `wager_transactions` (new migration, nullable for rows written before it); worker events reuse the original request's id. Rejected: a new id per retry.
- **Q2 Counting the 10 attempts.** (a): the request's own lookup is not an attempt; the row is due at once (S6 Q1); after worker attempt k the next one is `min(60s, 1s × 2^(k-1))` later, so attempts run at 0, 1, 3, 7, 15, 31, 63, 123, 183, 243 s and the window is about 4 minutes. ADR-05 is corrected from "about 5 minutes".
- **Q3 Data of `WagerTransactionPendingReference`.** The data of `WagerTransactionProcessed`, no new field, emitted once when the row starts to wait.
