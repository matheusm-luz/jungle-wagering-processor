# S8 — Read side

**Goal:** a provider can read a transaction by id and by provider + external id, page a wallet's ledger with a stable opaque cursor, and reconcile a wallet whose divergence is logged, counted and flagged but never fixed.

Requirements: R-44 (transaction queries), R-45, R-49; the trial-balance check of ADR-12.

## Tasks

- [x] T1 **Ledger cursor (L-13).** Base64url of `<walletId>:<last sequence read>`; `decode` refuses anything that is not the encoding of a positive integer for that wallet. Test: `test/unit/infrastructure/ledger-cursor.test.ts` "round-trips a sequence", "refuses a cursor of another wallet (S8 review, m5)", "refuses a cursor that is not one of ours". - [x] T3 **Transaction queries.** `GET /wagering/transactions/:transactionId` and `GET /providers/:providerId/wagering/transactions/:externalTransactionId` answer the same body: identity, kind, money, status, `failureCode`, reference, observed `balance` (absent for `WALLET_PLAYER_MISMATCH`, L-20), `createdAt`, `processedAt` (only once `PROCESSED`). Unknown → 404 `TRANSACTION_NOT_FOUND`; id not a UUID or an invalid identifier → 400. Files: `src/application/get-transaction.ts`, `errors.ts`, `ports.ts` (`WalletQueries`), `mikro-orm-wallet-queries.ts`, `wagering.controller.ts`, `app.module.ts`.
- [x] T4 **Ledger page.** `GET /wallets/:walletId/ledger?cursor=&limit=` (default 50, at most 200): entries in ascending `sequence` after the cursor, `nextCursor` (the last sequence returned, or the incoming cursor when the page is empty, so a reader can resume) and `hasMore` (read `limit + 1`). A reader stops on `hasMore === false`, not on a null cursor (S8 review, m4). Unknown wallet → 404; bad cursor, a cursor of another wallet or bad limit → 400. The `OPENING` behind the first entry is readable through the transaction routes (S8 review, m6). Test: "pages a wallet ledger in sequence order and resumes from nextCursor", "the default page is 50 entries", "a wallet opened at zero starts at sequence 2, and an untouched one has an empty ledger", "an unknown wallet is 404, and a bad cursor, a cursor of another wallet or a bad limit is 400". Files: `src/application/get-ledger.ts`, `ports.ts`, `mikro-orm-wallet-queries.ts`, `wallets.controller.ts`, `app.module.ts`.
- [x] T5 **Cursor under concurrent writes (R-45).** One walk of 3-entry pages; after each page, three parallel writes commit before the next page, so the walk is in progress while the wallet grows by construction. The walk sees every entry exactly once, in strictly ascending sequence. Test: "the cursor walks every entry once while the wallet is written". No new code expected (keyset on `UNIQUE (wallet_id, sequence)`).
- [x] T6 **Reconciliation endpoint.** `POST /wallets/:walletId/reconciliation` answers the statement body (`storedBalance`, `calculatedBalance`, `difference`, `consistent`, `checkedEntries`) from **one SQL statement**: wallet row, credit sum, debit sum and entry count in one snapshot, no lock. Test: "a consistent wallet reconciles with difference 0.00 and its entry count", "a wallet opened at zero checks 0 entries; an unknown wallet is 404". Files: `reconcile-wallet.ts`, `ports.ts`, `mikro-orm-wallet-queries.ts`, `wallets.controller.ts`.
- [x] T7 **Divergence is logged, counted, flagged, not fixed (R-49).** A balance tampered through SQL answers `consistent: false` with the difference, logs `wallet reconciliation divergence` (wallet id, no amounts), increments the divergence counter (per Q1), and the stored balance is still the tampered one afterwards; the test restores it before the ledger invariant. Test: "a balance tampered through SQL is reported, logged and counted, and not fixed".
- [x] T8 **No false divergence under load.** Three readers reconcile back to back while 20 parallel `BET`s run; every answer is `consistent: true`, and more than one stored balance is seen, which proves the reads overlapped the writes (S8 review, m2). Test: "reconciliation never reports a divergence while the wallet is written".
- [x] T8b **Reads never wait for the wallet lock (S8 review, m3).** With the wallet held `FOR UPDATE` by the test and a `BET` blocked behind it, the ledger page, the reconciliation and the transaction query answer 200 within 2 s. Test: "reads never wait for the wallet lock".

## Subtle points

- **Transaction boundary.** Reads run on a forked `EntityManager` without a transaction. Reconciliation is one statement so that the stored balance and the ledger sums come from the same snapshot at `READ COMMITTED`; two statements could see a commit in between and report a divergence that does not exist.
- **Lock.** None. Reads never take the wallet lock, so reconciliation and paging never slow down wagering (T8b).
- **Idempotency.** Not touched: reads only. Reconciliation is a `POST` in the statement but writes nothing, so it is safe to repeat.
- **Ack, outbox.** Not touched.
- **Money.** Sums come from SQL as decimal strings; the difference comes from `Money.subtract`, never `Money.from`, because it can be negative. A per-wallet credit sum beyond `NUMERIC(19,2)` (10¹⁷ of turnover) is refused by `Money.from`: documented limitation.

## Decisions (Matheus, 13 Nov)

- **Q1 — The divergence metric before S11: (a).** A minimal `Metrics` port now, with an in-memory counter that S11 exposes in `/metrics`; the test reads it from the app. Rejected: log only and count in S11.
- **Q2 — Trial balance (ADR-12): (b).** In the transfer-row model every row is balanced, so Σ wallet balances + Σ system-account nets = 0 per currency follows from the per-wallet reconciliation. A check in `test/support/ledger-invariant.ts`, which every test runs, plus the ADR-12 sentence saying why it is implied. Rejected: a `GET /ledger/trial-balance` endpoint; only the ADR sentence.
- **Q3 — Observed balance on the transaction queries: (a).** Same rule as `POST`: balance absent only for `WALLET_PLAYER_MISMATCH` (L-20). The remaining exposure through guessable external ids is the ADR-08 limitation. Rejected: no balance on reads.

## Notes from implementation

- **Q1 as built.** The counter is `Metrics` in `src/infrastructure/metrics/`, not an application port: the divergence is logged and counted at the HTTP edge (`WalletsController.reconcile`), next to its log line, so the application layer needs no port for it. S11 may move counting into a port when use cases need it (transactions by status, duplicates). The counter counts reconciliations that found a divergence, not divergent wallets: three calls on one broken wallet add 3 (S8 review, m7).
- **T9 as built.** `TRIAL_BALANCE` in `findLedgerProblems`; its `walletId` field carries the currency, so every union branch now returns the key as `text`.
- **Test order.** T1, T2 and T9 were test-first and seen failing for the expected reason (missing module; no `TRIAL_BALANCE`). The integration tests of T3 to T8 were written before the code but first run after it; one expectation was wrong in the test itself (a `REJECTED` row has no `processedAt`) and was corrected to the real contract. The review fixes (m1, m2, m3, m5, m6) changed tests and code together, not test-first.
- **Mutation runs.** (1) Reconciliation as two statements, the balance read after the sums, with no delay added: "reconciliation never reports a divergence while the wallet is written" failed 3 out of 3 runs on `consistent === true`. A first attempt at this mutation did not compile and was discarded, not counted. (2) `select … for update` on the wallet added to the ledger page: "reads never wait for the wallet lock" failed after its 2 s timeout. T5 passes by construction of the keyset; not mutated.
