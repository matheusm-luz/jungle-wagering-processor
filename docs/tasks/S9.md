# S9 — SQS consumer

**Goal:** every instance consumes `wager-transactions.fifo` through the same `ProcessWagerTransaction` as HTTP, records the message in the inbox inside the same SQL transaction, acks only after commit, retries transient failures with visibility backoff, dead-letters permanent ones itself, and on `SIGTERM` finishes or returns its in-flight messages.

Requirements: R-52, R-53, R-54, R-55, R-56, R-68; L-08 on SQS.

## Subtle points

- **Transaction boundary.** Inbox row, transaction, ledger entry, wallet and outbox in one `em.transactional()`. The inbox insert is the first statement; a duplicate stops before the wallet lock. An unknown wallet commits the inbox row alone (L-08).
- **Lock.** Unchanged: the wallet row. The inbox primary key serialises two deliveries of one message the way the idempotency index serialises one key. `lock_timeout` turns a long wait into a transient error.
- **Idempotency.** Two layers: inbox `(consumer_name, message_id)` for the message, idempotency key for the business request, so a new message carrying an old key is a replay (same hash across transports, ADR-03).
- **Ack.** `DeleteMessage` only after `executeMessage` returned, i.e. after `COMMIT`. A crash in between is a redelivery the inbox absorbs (T9). Permanent failures: DLQ send before delete, so a crash leaves the message in the source queue, never lost.
- **Outbox.** Untouched: rows written as in HTTP; publication is S10.
- **Ordering.** One message per receive per loop: SQS FIFO hands out no further message of a group while one is in flight, so per-wallet order holds across loops and instances without code. A transient failure blocks its group until it succeeds or is dead-lettered, which is what FIFO ordering means.

## Decisions (Matheus, 13 Nov)

- **Q1 — 409 conflicts on SQS: (a) permanent → DLQ.** `IDEMPOTENCY_KEY_CONFLICT` and `EXTERNAL_TRANSACTION_CONFLICT` are not persisted (ADR-03); the message can never succeed and a human must look at it. Rejected: ack with log, metric and inbox row, like L-08.
- **Q2 — Lock timeout: (a) now, HTTP 503 in S12.** `DATABASE_LOCK_TIMEOUT_MS` is the realistic transient failure the DLQ test needs. Rejected: mapping 503 now; a test-only failpoint instead of a lock timeout.
- **Q3 — Consumer concurrency: (a) N loops of one message each, N = 5 by default.** First answered (b), batches of 10; changed to (a) once the cost was stated: SQS increments `ApproximateReceiveCount` for every message a receive returns, so in a batch the messages of a group behind a failing head are skipped to keep order yet still count receives, and the redrive policy would dead-letter up to nine of them without one attempt. With one message per receive, FIFO hands out nothing else of the group while the head is in flight.

## Notes from implementation

- **Test order.** T1, T2, T3 and T4 were test-first and seen failing for the expected reason (missing module; no `scope.inbox`; no `executeMessage`; a lock wait that never ended). For T6 to T8 the consumer class was written first and the integration file second; the file was then run before the consumer was registered in `AppModule` and all 11 cases failed on "condition not met", then passed once it was. T9 to T11 were written after the consumer and passed on their first run except the two `SIGTERM` cases (next note).
- **Long poll on shutdown (found by T10).** The first version aborted the open long poll on `SIGTERM`. The two `SIGTERM` cases then failed whenever they ran right after a test that had stopped a process: LocalStack handed the next message to the poll the stopped process had abandoned, and it stayed invisible for its 30 s visibility timeout with nobody working on it. The consumer now lets the open poll end (`SQS_WAIT_TIME_S`, default lowered from 20 to 10 s) and hands back at once a message it brings; Compose gives the app 30 s to stop, and the test container sets `SQS_WAIT_TIME_S=1` so every app the suites close stops within a second. The new default first broke `health.test.ts` (each `close()` waited 10 s past a 5 s hook): fixed by that test setting, not by weakening the test.
- **A test-helper bug (T8).** The DLQ is FIFO: a message the test read and left in flight blocked the next one of its group. `take` now deletes what it reads.
- **Mutation run.** `DeleteMessage` moved before `executeMessage`: both transient-failure cases of `sqs-consumer.test.ts` failed (the message was gone before the retry). Restored.
- **Metrics.** Counters `sqs_duplicate_messages`, `sqs_unknown_wallet_messages`, `sqs_message_retries`, `sqs_messages_dead_lettered` in the S8 `Metrics`; S11 exposes and names them for `/metrics`.
- **Correlation id.** The envelope `messageId`, so a redelivery and the events of the transaction correlate with the message (L-15 extended to SQS); `correlation_id` is `text`.
- **Inbox hash.** The transaction's payload hash, which leaves out `data.idempotencyKey`: the same message id with the same business fields under another key is a duplicate, not a conflict. Accepted as is; a stricter hash would need its own canonical form.
